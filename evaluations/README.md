# 评估

`examples/` 回答「产物长什么样」。`evaluations/` 回答另一个问题：

> 把一本真正的长篇交给这套技能，按文档从头走一遍，它还跑得通吗？

两者的差别不是规模，是**来源**。`examples/golden-project` 是手工塑形的样例——
干净、小、每条引用都对，适合看清目录与引用链的形状。但它塑形自我们自己的想象，
所以它只覆盖我们想到过的情况。

三个缺陷从它旁边走了过去：时长估算把画外音计零秒、配音本在结构上装不下画外音、
重建索引会静默重编块号。三个都不是疏忽，都是**样例里没有那种输入**：
`golden-project` 八集剧本里 `[VO]` / `[OS]` 出现 0 次，没有配音本，
没有一份被修订过两次的剧本，也没有一本 147 KB 的原著。

| 目录 | 来源 | 覆盖 |
|---|---|---|
| [让你管账号/](让你管账号/) | 一部完整长篇（20 章 / 147 KB / 52,552 字），按文档实跑 | 原著索引、画外音、完整配音本、改稿后的索引重建、21 个产物的完整生命周期 |

## 每次发布前要做什么

分两层，因为两层能判定的东西不同。

### 1. 回归闸门（脚本，随测试跑）

```bash
python3 -m unittest tests.test_workflow_evaluation
```

它把录下来的那一次运行重新过一遍全部检查器，并核对派生层还能从各自的源头重建：
章节索引能否从原著重算出同一张表、剧本索引重建后块号是否一字不动、
配音本是否覆盖全部口播行、时长是否仍在声明容差内、21 个产物是否都还是 `accepted`。

**这一层判定的是「没有退步」，不是「做得好」。**它不看戏写得怎么样。

### 2. 主工作流实跑（人或 Agent，发布候选上做一次）

闸门跑的是**录下来的结果**；这一步跑的是**流程本身**。开一个新项目，
只给它 `让你管账号/reference-run/输入/` 里那份原著，按各技能 SKILL.md 从头走到
EP001 的视频提示词，然后与 `reference-run/` 对照。

对照的不是文本相同——创作产物每次都不一样，这很正常。对照的是：

- **哪一步需要人替系统解决问题**，以及是不是新出现的（`reference-run/RUN-LOG.md` 记着上一次的清单）；
- **哪个检查器报错**，报的是不是同一类；
- 文档说的做法**是不是真的能走通**——上一轮最重的一个缺陷正是这一条：
  `SKILL.md` 写的重建方式与脚本的实际行为不一致，而所有测试都是绿的。

发现的问题按 `CONTRIBUTING.md` 的分类记进 `CHANGELOG.md`。
**这一步不比较两套 pipeline，也不产出胜负判定**——它只回答「我们自己的流程现在还顺不顺」。
